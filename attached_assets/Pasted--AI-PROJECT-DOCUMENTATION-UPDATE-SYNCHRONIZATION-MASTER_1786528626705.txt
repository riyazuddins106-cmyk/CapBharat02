# AI PROJECT DOCUMENTATION — UPDATE & SYNCHRONIZATION MASTER PROMPT

You are maintaining the project's official AI-readable development documentation.

Your job is NOT to rewrite the entire documentation unnecessarily.

Your job is to **inspect the current project, compare the documentation against the actual codebase, identify what changed, and update the documentation so that another AI can continue development without repeating previous work or breaking existing functionality.**

---

# 1. PRIMARY OBJECTIVE

Keep `/docs` synchronized with the **actual current state of the project**.

The documentation must allow a new AI agent to understand:

* What this project is
* What the project does
* How the architecture works
* Which technologies are used
* How the database works
* How APIs work
* How Customer, Partner, and Admin applications work
* What has already been implemented
* What is currently working
* What is currently broken
* What is partially implemented
* What has been fixed
* How issues were fixed
* Which fixes must NOT be repeated
* What remains to be done
* What must NOT be changed
* What errors have occurred
* What tests have already been performed
* What the latest development state is

The documentation must function as the project's **AI Development Memory**.

---

# 2. VERY IMPORTANT — DO NOT ASSUME

Never assume that an old documented issue is still present.

For every documented issue:

1. Check the documentation.
2. Inspect the relevant source code.
3. Check the current implementation.
4. If possible, run the relevant application/test.
5. Determine whether the issue is:

   * OPEN
   * FIXED
   * PARTIALLY FIXED
   * REGRESSED
   * NOT REPRODUCIBLE
   * OBSOLETE

The actual current code/runtime state has priority over outdated documentation.

---

# 3. DO NOT RE-FIX EXISTING FIXES

Before modifying any code, search:

* `/docs/22-FIXED-ISSUES.md`
* `/docs/31-FIX-HISTORY.md`
* `/docs/40-CHANGELOG.md`
* `/docs/20-CURRENT-STATUS.md`
* `/docs/24-DO-NOT-CHANGE.md`

If the requested issue is already documented as FIXED:

DO NOT implement the same fix again.

Instead:

1. Verify whether the fix is still present.
2. Verify whether the problem has actually returned.
3. Only modify code if a genuine regression is confirmed.
4. Record the regression separately.

Example:

BAD:

> Documentation says partner profile image was fixed. I will implement the profile image fix again.

CORRECT:

> Documentation says partner profile image was fixed. I will inspect the current implementation and verify whether the issue still exists. If it works, I will not modify it.

---

# 4. DO NOT CHANGE WORKING FUNCTIONALITY

Do NOT:

* redesign the application
* rewrite working modules
* replace architecture
* replace libraries
* change database structure unnecessarily
* change working APIs unnecessarily
* change UI unnecessarily
* refactor unrelated code
* remove existing functionality
* duplicate existing functionality

unless explicitly requested.

The objective is:

**MINIMUM NECESSARY CHANGE.**

Do not document assumptions.

# 8. WHEN A BUG IS FIXED

Whenever you confirm a bug is fixed, update:

```text
20-CURRENT-STATUS.md
21-KNOWN-ISSUES.md
22-FIXED-ISSUES.md
31-FIX-HISTORY.md
32-TESTING-STATUS.md
40-CHANGELOG.md
```

as appropriate.

Record:

* Issue ID
* Problem
* Root cause
* Solution
* Files changed
* Date
* Testing performed
* Result
* Any important side effects
* Whether future AI agents should avoid modifying the implementation

Example:

```text
BUG-014

Problem:
Partner profile image was not displayed in Partner App.

Root Cause:
Partner API response did not include the profile image URL.

Solution:
Updated the partner response mapping to include profileImage.

Files Changed:
- server/src/routes/partner.ts
- apps/partner-mobile/src/screens/Profile.tsx

Status:
FIXED

Verification:
Verified through API response and Partner App UI.

AI Instruction:
Do not reimplement this fix unless a regression is confirmed.
```

---

# 9. WHEN A BUG IS STILL OPEN

Do NOT mark it fixed just because code was changed.

Use:

```text
Status: IN PROGRESS
```

or:

```text
Status: OPEN
```

Record:

* What is wrong
* Where it occurs
* Steps to reproduce
* Error message
* Relevant API
* Relevant files
* Suspected cause
* What has already been attempted
* What remains

---

# 10. WHEN A FIX FAILS

Record failed approaches.

This is extremely important for future AI agents.

Example:

```text
Attempt 1:
Changed frontend API URL.

Result:
FAILED.

Reason:
The actual issue was server-side CORS configuration.

Do not repeat this approach unless new evidence indicates the situation has changed.
```

This prevents future AI agents from repeatedly trying the same failed solution.

---

# 11. REGRESSION HANDLING

If something that was previously FIXED becomes broken again:

DO NOT overwrite the original fix history.

Create a new regression entry.

Example:

```text
REG-003

Original Issue:
BUG-014

Problem:
Partner profile image stopped displaying after API refactor.

Previous Fix:
BUG-014

Current Cause:
Partner serializer was changed during API refactor.

Status:
REGRESSION

Action:
Restore the required profileImage mapping without changing unrelated functionality.
```

* API endpoints are correct.

**Update the documentation.**

**Fix the code only if the task requires it or the documented issue requires it.**
